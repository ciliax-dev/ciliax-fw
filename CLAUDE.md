## Project

**ciliax-fw** — embedded firmware framework for on-device acoustic event detection on Nordic nRF Connect SDK. C++20, hexagonal architecture, swappable ML models. Targets the nRF5340 family today; nRF91 cellular variant planned.

## Architecture (read this carefully — it drives most decisions)

Hexagonal / ports-and-adapters, four layers:

```
app/src/
├── domain/             ← pure C++ logic, NO Zephyr includes
├── ports/              ← abstract interfaces, NO Zephyr includes
├── adapters/
│   ├── zephyr/         ← Zephyr-using implementations
│   └── mock/           ← test doubles, NO Zephyr includes
└── main.cpp            ← composition root, the ONLY place that wires
                          domain + adapters + Zephyr together
```

**The single most important rule:** `domain/`, `ports/`, and `adapters/mock/` must never `#include <zephyr/...>` or any Nordic header. Run this check before claiming a task is done:

```bash
grep -r --include='*.cpp' --include='*.hpp' --include='*.h' \
    '#include <zephyr/' app/src/domain app/src/ports app/src/adapters/mock
```

If it returns anything, the architecture is broken — fix before continuing.

Ports are the seams that make the rest of the system testable. Every external dependency (clock, GPIO, BLE, network, sensor, classifier) is reached through a port. Domain code only sees interfaces.

## Tech stack

- **NCS:** v3.2.x, pinned in `west.yml` to a release tag (never `main`)
- **Build:** west + CMake + Kconfig + Devicetree (standard Zephyr stack)
- **Language:** C++20 (`CONFIG_STD_CPP20=y`). Minimal C++ runtime — full libstdc++ deliberately *not* linked, so heap-allocating standard containers (`std::vector`, `std::string`, `std::map`, `<iostream>`) compile but fail at link. Use ETL for runtime containers — wired up via `west.yml` at `<workspace>/modules/lib/etl/`. See [`docs/cpp_subset.md`](docs/cpp_subset.md) for how this is achieved (Zephyr's `MINIMAL_LIBCPP` + selective re-exposure of the toolchain's libstdc++ headers via the `ciliax_add_cxx_includes()` helper in [`cmake/zephyr_cxx_includes.cmake`](cmake/zephyr_cxx_includes.cmake), called from `app/CMakeLists.txt` and any other Zephyr-built target).
- **Test framework:** GoogleTest for host unit tests; ztest for `native_sim` integration
- **CI / reproducible build:** GitHub Actions; `zephyrprojectrtos/ci` Docker image pinned by digest, driven by `scripts/build.sh`. (`nordicplayground/nrfconnect-sdk` was the original plan but stopped publishing tags after `v2.9-branch`; it has no v3.x image.)
- **Format/lint:** clang-format (LLVM-derived), clang-tidy (advisory at first)

## C++ subset

See `docs/cpp_subset.md` for the canonical list. Quick reference:

- **Use freely:** `constexpr`/`consteval`, `std::array`, `std::span`, `std::optional`, `std::expected` (or `tl::expected`), ETL (`etl::vector<T, N>`, `etl::string<N>`, `etl::map<K, V, N>`, `etl::delegate`), strong types, RAII, `enum class`, lambdas, structured bindings, `[[nodiscard]]`
- **Use carefully:** virtual functions (avoid in ISRs), `std::function` (heap risk — prefer templates or `etl::delegate` in hot paths)
- **Forbidden / not available:** exceptions (`-fno-exceptions` is set), RTTI, heap after init, `std::vector`/`std::string`/`std::map`/`<iostream>` (full libstdc++ not linked, link will fail), globals with non-trivial constructors that depend on each other

When in doubt, prefer compile-time over runtime, prefer `std::array<T, N>` over `T[N]`, prefer `std::span` over raw pointer + size.

## TDD discipline

This project is TDD. Two-pass workflow for any new behavior:

1. **Write the failing test first.** Build it. Confirm it fails for the *right reason* (compile error or assertion mismatch — not a typo). Report the failure.
2. **Implement the minimum** to make it pass. Refactor if needed. Confirm green.

Do not write tests and implementation in the same edit. The failing-test step is not optional — it's how we know the test actually tests something.

Domain code should always be unit-testable on the host with no Zephyr involvement. If a piece of logic is hard to test, the architecture is wrong, not the test.

## Workflow conventions

- **`main` is human-only.** Claude never commits directly to `main`. All Claude work goes on a `feature/<short-name>`, `fix/<short-name>`, or `refactor/<short-name>` branch and lands on `main` only when a human merges the PR. If a session starts on `main` with changes to make, switch to a branch first.
- **Branches:** `feature/<short-name>`, `fix/<short-name>`, `refactor/<short-name>`
- **Commits:** conventional-style is fine but not enforced. Imperative mood ("add MFCC computation", not "added MFCC computation"). Body explains *why* if non-obvious.
- **No commits with failing tests on shared branches.** Squash WIP locally before pushing.
- **PR descriptions** state: what changed, why, how it was tested, anything reviewers should look at carefully. No template ceremony.
- **Docs land in a dedicated follow-up commit.** Whenever a task lands a lasting effect — completing a phase plan step, swapping a tool, adding/removing a dependency, changing a build path, or any decision that diverges from a doc — finish the implementation commit(s) first, then create a separate commit (typically titled `docs: …`) updating the affected docs. Keep code and docs in different commits so a reader bisecting or reverting one doesn't accidentally take the other. Targets in priority order: the relevant phase plan in `docs/phases/`, then `CLAUDE.md`, `README.md`, and `docs/<area>.md`. Record what's done and any plan deltas; divergences left only in chat history or commit messages are invisible to the next reader of the repo. This applies even when the user did not explicitly ask for the doc update.
- **Phase plan status is tracked live, per step.** The Status table in the active `docs/phases/phaseN.md` is the single source of truth for "where are we." Every step row carries one of three states: `not started` → `in progress` → `done`.
  - **Before** starting work on a step, flip its row from `not started` to `in progress`. Do this in the working tree even if no commit is made yet — it signals to the next session (or a parallel agent) that the step is taken. If your first commit on the step is the right place to land it, include the flip there; otherwise it can ride along with the implementation commit.
  - **After** the step's success criteria are met (verification block green, tests passing, etc.), flip `in progress` to `done` in the per-step `docs:` follow-up commit, alongside any plan deltas. Do not bundle multiple steps' status flips into one commit — each step gets its own status update so `git log -- docs/phases/phaseN.md` reads as the project's progress timeline.
  - Never declare a step done in chat without flipping its row in the same session. If you find yourself "skipping the docs update for now," stop and write the docs commit — leaving the table stale defeats the point of having a phase plan.

## Verification before declaring "done"

For any task touching code, run *all* of these and confirm green before declaring it complete:

```bash
# 1. Architecture invariant
grep -r --include='*.cpp' --include='*.hpp' --include='*.h' \
    '#include <zephyr/' app/src/domain app/src/ports app/src/adapters/mock
# (should return nothing)

# 2. Host unit tests, with sanitizers
cmake -S tests/host -B tests/host/build-asan -DENABLE_SANITIZERS=ON
cmake --build tests/host/build-asan -j
ctest --test-dir tests/host/build-asan --output-on-failure

# 3. Firmware build (matches CI)
west build -b nrf5340dk/nrf5340/cpuapp app --pristine=auto

# 4. Integration tests on native_sim
west twister -T tests/integration -p native_sim --inline-logs

# 5. Format check
clang-format --dry-run --Werror $(find app/src -name '*.cpp' -o -name '*.hpp')
```

If any of these fail, fix before claiming the task is done. Don't suppress warnings, don't disable failing tests, don't lower compiler strictness to make CI green — root-cause it.

## Things to avoid

- **`revision: main` in west.yml.** Always pin to a release tag.
- **`file(GLOB)` for sources where order matters,** or where new files might silently change behavior. Globbing is fine for the existing top-level `app/src/domain` and `adapters/zephyr` patterns where order is irrelevant.
- **Heap allocation in steady-state code.** Initialization is fine; the main loop should not allocate.
- **Logging from ISRs.** Defer to a work queue.
- **C99 designated initializers in `.cpp` files.** They don't compile in C++. Some Zephyr headers (notably `<bluetooth.h>`) require this — handle BLE init in a small `.c` wrapper file and call from C++.
- **`std::endl` in embedded code.** Forces flush. Use `'\n'`.
- **Reaching into Zephyr internals from domain code** "just for this one thing." If you find yourself wanting to, the port is missing.

## When asked about an unfamiliar piece

Before guessing about Zephyr APIs, NCS specifics, or board files: read the relevant header in `zephyr/include/` or `nrf/include/`, or check `docs.nordicsemi.com`. Hallucinating a function signature wastes more time than looking it up.

If you're unsure whether an approach will work on the chip, write a small test on `native_sim` first. Cheaper than a flash-and-pray cycle.
